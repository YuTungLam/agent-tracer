# Paired Report Visualization Requirements

This document defines the presentation contract for future clean-versus-attacked HTML reports generated by `agentdojo_lab.paired_report`.

Updated 2026-09-17 after the researcher rejected a primarily textual event viewer.
Conversation may be in Chinese; code, HTML and Markdown must remain English.

## Required views

1. Preserve the existing comparison scope, overview, action-alignment table, links to each per-run report, execution chains, and recorded event details.
2. Put actual diagrams first: an SVG source-to-action overview and a two-lane, clickable SVG event flowchart. Colored text boxes, JSON tables, or lists of buttons alone do not satisfy the visual requirement. Selecting a node must update the aligned clean and attacked details together.
3. Label both arms explicitly as **Clean** and **Attacked** in the selector, event details, and source-evidence panels. Event identifiers are local to their run and must retain their arm label.
4. Show field-level differences using stable JSON paths. Visually distinguish changed values, values added in the attacked run, and values missing from the attacked run. Missing events and missing values must remain visible rather than being converted to `null` or omitted.
5. For the selected events, show source results and `TOOL_OUTPUT_EXPOSED` records linked to the same model request. Separate the clean source evidence from the attacked source evidence and retain the recorded content needed to inspect an injected instruction.
6. Keep unsuccessful attacks, source omissions, parser failures, runtime errors, and unknown evidence visible.
7. Make readable content the default. Display recipient, subject, message body, file and other argument values as labeled content cards. Highlight changed words inside the values, in addition to typed JSON-path differences. Keep full JSON under a separate **Raw evidence** tab and the previous tables under a collapsed disclosure.
8. Default to a changed sensitive argument when available, while retaining its uncertainty status. Support direct links and searches for recorded event IDs (such as events 34 and 37); never substitute the event sequence number for the event ID.
9. Provide a **Sources** tab with clean and attacked content side by side, source-result and exposure-event buttons, and the outbound request identity. Align these sources through recorded event bindings, not their array positions. Keep unresolved references and unmatched sources explicit.
10. Allow switching the source displayed in the overview. The initial source is chosen for visible content difference as a reading aid; this ordering is not a causal ranking or attribution result.

## Interpretation boundaries

The visualization may establish recorded exposure, content correspondence, proposal differences, execution, and observed environment changes. It must not describe exposure or correspondence as proof of causal influence. A proposed tool call is not proof of execution, and attack success must come from the separately declared native state oracle.

Event pairing is a navigation aid. The report must disclose that ambiguous action alignments are hypotheses and preserve the underlying raw evidence for independent inspection.

Solid overview arrows describe recorded order; dashed links describe source/request
association. A raw model response and its parsed proposal are separate recording
stages, not two independent model decisions. Transport identifiers and usage metadata
are separated from readable content differences but remain available verbatim.

## Delivery constraints

- Produce a self-contained, offline HTML file with no external scripts, fonts, images, or network requests.
- Escape recorded model and tool content before inserting it into HTML.
- Support keyboard-operable controls and responsive clean/attacked panels.
- Use English for generated HTML, code, and project Markdown.
- Generate the view from saved run evidence without modifying either source run.
- Generate versioned single-run copies when existing HTML hashes are bound into
  historical receipts. A requested derived landing page may be refreshed with
  its previous bytes backed up; preserve its `pair.json` and all original run inputs.

## Implementation and verification

The shared paired view uses `src/agentdojo_lab/paired_report_data.py` and the
`templates/paired_report.html`, `.css` and `.js` assets. The single-run template is
`templates/run_report.html`. See [the visual library guide](VISUAL-REPORT-LIBRARY.md)
for batch rebuilding and the coverage of archived report formats.

Validation must include meaningful data/escaping/alignment tests and a real browser
check of node selection, source navigation, highlights, and desktop/mobile layout
when a browser is available. JavaScript syntax alone is not visual verification.
