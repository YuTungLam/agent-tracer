## 重复、运行单位与停止规则

- 预先计划 10 个不同任务 × 3 次 = 30 个 trial。先执行完整第 1 轮的 10 个 trial；检查工程链路后再执行第 2、3 轮。各轮保持相同任务顺序，不按效用分数重新排序。
- 每个 trial 是独立子进程、独立原生环境和独立 run 目录；run 级 tokens、时间属于该任务的这次 trial。原生 pipeline 内部的最多 3 次尝试仍属于同一个 trial，不计为独立重复。
- 批次固定配置、协议、任务 prompt、上游 commit、依赖锁和实现源码哈希。恢复时拒绝更改配置或实现，避免不同版本混入同一批次。
- SDK 不重试；批次不重跑已经开始的 trial。`--resume` 只处理从未开始的预定槽位，包括中断之前尚未执行的任务。任务失败、API 错误、超时和不完整记录均保留。
- 单 trial 硬超时 600 秒（包括配额等待）；请求 timeout 60 秒，单次工具循环最多 8 轮，单请求 completion 上限 4096 tokens。超时终止其子进程并保存批次级 execution 状态，保留已有原始文件。原生重试和多次请求意味着这些设置不是整个 trial 的 token 硬上限。
- 同一批次跨 trial 共享客户端请求节奏控制：65 秒窗口内预算 7,000 tokens，按请求 JSON 字节数 / 3 加 1,024 输出余量估算预留，响应完成后以 API 报告的实际总 tokens 替换。估算不是服务端 tokenizer；超出预算的单请求独占窗口但仍可能被服务拒绝。只延迟发送，不改请求内容、不重试请求，不在状态文件保存文本或密钥。
- HTTP 401、403、429 会使批次停止派发后续任务并记录 `service-pause.json`，不重试已开始槽位。批次自身不增加 trial 间固定等待。实际请求数和 API 报告用量落盘；不从 tokens 推算未经验证的货币费用。

第 1 轮的工程检查包括：每个开始的 trial 均有可解释的终态；成功采集的日志通过内部审计；HTML 和批次索引能定位到原始记录。utility 失败不会阻止进入重复轮。若存在采集缺口或系统性接入故障，先保留本批次并诊断；修改实现后应另建批次，不能覆盖旧结果。

## 汇总指标与分母

- 原生任务效用：分别列出通过、未通过、无法评估；同时列出已开始、已完成、可评估和计划 trial 数。未运行槽位不是失败，API 故障不是 evaluator 给出的 utility=false。
- 记录质量：逐 trial 显示 `recording.complete` 和重新执行的事件审计；二者不可被 utility 覆盖。审计只检查保存记录的内部一致性，不证明没有遗漏任何未被观测的内部操作。
- 过程覆盖：实际 runtime 工具集合、各类事件数、多调用响应数、环境变化事件数、工具输出进入后续请求的数量。关联型指标仅在事件审计通过时计算。
- “已有工具输出的请求又提出新调用”只表示存在后续来源分析机会，不能证明该调用使用了这些输出。
- 成本：每 trial 的 SDK 请求数、API 报告输入/输出 tokens、原始 run elapsed、子进程总耗时、`pacing_wait_seconds` 和 events.jsonl 文件字节。run elapsed 包含配额等待；配额等待不是 tracer 耗时，也不属于服务端推理延迟。run elapsed 与进程总耗时测量范围不同，分别保留。
- 不把 30 个 trial 称为 30 个独立任务；跨任务覆盖为 10。这里只做描述性表格，不据此声称显著性、整体 benchmark 成功率或真实线上非干扰。

## 非干扰与开销的后续验收

已有固定响应下的请求、工具行为、历史和环境一致性测试。本轮真实轨迹用于扩充正常流程覆盖；真实模型重复输出不同不自动表示采集器干扰。

独立开销实验应冻结同一正常响应序列，在相同环境下交替运行采集开/关条件，分别计时并校验输入与状态一致。真实 Groq 总耗时还包含服务端与网络波动，不能用两次 elapsed 相减就宣称 recorder overhead。本轮存储和总耗时只作为后续对照设计的观测数据。
